# 06. デバイス展開・オフライン・セーブデータ取り回し

「HTMLベースならデバイス横展開が楽」という前提を、**保存**の観点で成立させるための設計。表示はどのブラウザでも動くが、ファイル保存はブラウザ差が大きい領域であり、ここが本ドキュメントの主題。

## 1. 基本モデル: ワークスペース + 明示的書き出し

```
[ZIP] ──取込──▶ [ワークスペース(ブラウザ内OPFS)] ──編集(自動保存)──▶ [書き出し/共有でZIP化]
```

- **作業中の正本はブラウザ内ワークスペース**（OPFS: Origin Private File System）に置く。1op毎に自ログへ追記flushされるため、クラッシュ・バッテリー切れでも消えるのは直前操作のみ
- ZIPは「持ち運び・受け渡しのための梱包」。作業のたびにZIPを書き換える方式は採らない（スマホでは任意ファイルへの追記が不可能なため、この分離が横展開の鍵）
- これにより「開く→編集→閉じる」だけならファイル操作ゼロ。ZIPに触るのは受け渡しの時だけ

## 2. プラットフォーム対応マトリクス

| 能力 | Win/Mac Chrome・Edge | Mac Safari | iOS Safari/PWA | Android Chrome/PWA |
|---|---|---|---|---|
| OPFSワークスペース | ○ | ○ | ○ (16.4+) | ○ |
| ZIP取込（picker/D&D） | ○ | ○ | ○（Filesアプリ/Drive経由） | ○ |
| 元ZIPへの上書き保存（File System Access API） | ○ | × | × | △（一部） |
| 共有シートでZIPを送る（Web Share files） | △ | ○ | ○ | ○ |
| ダウンロード保存 | ○ | ○ | ○（Filesへ） | ○ |
| PWAオフライン起動 | ○ | ○ | ○ | ○ |

結論: **全プラットフォームで「取込→編集→書き出し」が成立する**。差が出るのは書き出しの動線だけで、Platform Layer（docs/03）が最適な手段を自動選択する:

1. File System Access APIがあれば「元のZIPに上書き保存」（デスクトップChrome系の最良体験）
2. Web Share (files) があれば「共有…」→ Drive / LINE / AirDrop / メールへ直接（スマホの最良体験）
3. どちらも無ければ通常ダウンロード

## 3. スマホでのセーブデータ取り回し（ユーザー提起の論点）

**答え: 取り回せる。ただし「ファイルを直接編集する」のではなく「受信→取込→編集→共有で送り返す」という往復モデルになる。**

iOS実例フロー（最も制約が厳しい環境）:

1. LINEやDriveで `.lociview` を受け取る → 「LociViewで開く」またはFilesに保存してLociViewのホームから選択
2. 編集はワークスペースで自動保存。アプリを閉じても次回続きから
3. 送り返す時は「書き出し→共有シート」→ Drive/LINE/メールを選ぶ

これはスマホユーザーが写真でやっている操作と同型であり、学習コストが低い。差分ZIP書き出し（docs/05 §3.5、opsのみ数十KB）を使えばモバイル回線・メール添付でも軽い。

### ファイル関連付け

- PWAの `file_handlers`（Android/デスクトップ）で `.lociview` をダブルタップ起動に関連付ける。iOSはPWAの関連付け不可のため「共有→LociView」またはホームからの選択で代替

## 4. データ消失リスクと対策（スマホ特有）

ブラウザ内ストレージはOS/ブラウザに削除され得る（iOSの容量逼迫時削除、「サイトデータを消去」誤操作等）。対策を多層で:

1. `navigator.storage.persist()` を要求（インストール済みPWAでは概ね許可される）
2. **未書き出し変更の常時可視化**（docs/05 §5）+ 一定量の未書き出しopが溜まったら書き出しを促すリマインド
3. ホーム画面インストールを推奨する導線（インストール済みPWAはストレージ削除の優先度が下がる）
4. 思想として「ZIPが正本、ワークスペースは作業机」と案内で明言する。「書き出し=バックアップ完了」の心理モデルを作る

- 配布: GitHub Pages（現行LociMyuと同じ運用でよい。サーバサイド不要）。加えてシングルファイル版 `lociview.html` をReleasesで配布（docs/03 §3）

## 5.5 iOSメモリ対策（実機検証で判明・2026-07-21）

iOS SafariはタブのメモリがおおむねRAMの一部（機種により200〜400MB程度）で強制終了される。
実データ（38MB GLB + 画像52枚）の取り込みでタブがクラッシュし「問題が繰り返し起きました」に陥った。
原因と対策:

- **GLB読込時の無駄なコピー**: `new Uint8Array(bytes).buffer` で38MBの複製を作っていた
  → バッファをそのまま渡す（`loaders.ts`）
- **開くたびの自動モデル読込がクラッシュループを生む**: 大きいモデルを持つプロジェクトを開くと
  毎回自動でロード→クラッシュ→再読込…を繰り返す
  → `AUTO_LOAD_LIMIT`（25MB）超のモデルは自動読込せず、案内を出して手動表示に委ねる（`app.ts`）。
  これにより「開く」操作自体は必ず成功し、ユーザーが表示可否を選べる
- **取り込み時の全アセット同時保持**: OPFSへ書いたアセットのバイト列を都度解放（`importWizard.ts`）
- **手動表示の確認**: 25MB超のモデルはModelタブの「表示」前に確認ダイアログ
- **GLコンテキスト喪失の可視化**: 白画面のままにせず「端末のメモリが不足しました」を表示（`viewer.ts`→`app.ts`）

残る本質的制約: これらは「読める可能性」を上げるが、テクスチャの重いGLBは機種によっては
依然として表示できない。将来的にはGLBのテクスチャ縮小・ジオメトリ簡略化（取込時の任意ダウンサイズ）が必要。

## 6. 性能予算（デバイス横展開の現実線）

| 項目 | デスクトップ | スマホ（中位機） |
|---|---|---|
| メッシュ | 〜300万トライアングル | 〜50万トライアングル |
| 点群 | 〜500万点 | 〜100万点（超過時自動サブサンプル） |
| プロジェクトZIP | 〜2GB | 〜500MB目安（警告表示） |
| 画像 | 数千枚 | 数百枚（サムネイル優先ロード） |

- 取込時にPlatform Layerの端末クラス判定（deviceMemory等 + 実測）で警告・自動調整
- 画像はサムネイル（thumbs/）を先に出し、原寸はタップ時ロード。サムネイル未同梱ZIPには取込時生成
