# 完了済み編集コピーの原本検査タイミング案

> Status: `PROPOSED / ON HOLD FOR RECOVERY DESIGN / NOT APPROVED / NOT IMPLEMENTED`
>
> 2026-10-29。現在の契約と実装は変更しない。PO判断後に、適用する条項と
> 受入条件を確定してから実装する。現在の実行結果は[todo](../../tasks/todo.md)。

## 1. 解決する利用者の待ち時間

50万点GSの閲覧ファイルから編集コピーを作った後も、通常の本文編集や保存で
取込時の私的ZIP原本を繰り返し照合する。原本は約178MBあり、現在の契約は
完了済みの親子処理についても、この検査を各commandとSession読取に要求する。
今回の処理内GS解析の共有と表示用読取の整理では、この契約を緩めていない。

本案は、完了済み取り込みの検証済み結果を同じ作業セッションで使用し、通常の
編集・保存時には現在のProjectと小さい管理記録を検査する案である。期待する
効果は実装後に同じブラウザ操作で測る。短縮秒数や容量の新保証は設けない。
個々の検査の高速化や表示更新の整理も引き続き選択肢であり、本案だけが改善
方法であるとは判断していない。

## 2. 適用範囲

- 最初は01eのPC候補における、完了済みReview→私的Clean子処理だけを対象とする。
- 取り込み開始・未完了処理・初回の完了確認、明示的な再試行・復旧・新しい入力、
  Projectを開き直すときは従来どおり原本全体を検査する。
- 通常の本文・位置等の編集と現在のProjectからの保存・受け渡しでは、本案の
  条件を満たした同一セッション内に限り、完了済み取込原本の全体再検査を省く。
  現在のProjectのモデル・画像・履歴と、新しい出力ファイルの照合は省かない。
- 旧形式、通常PWA、一般採用・iPhone・offline・公開の方針は変更しない。
  現行形式・変換レシピ・容量制限・原本の保存内容も変更しない。

## 3. 使用できる検証済み結果

親Reviewのoriginal.zip/copy.zipと子Cleanのinput.zipを全体検査し、親子の
完了記録と初回publicationを正しく照合した後に限り、内部の一時的な検証結果を
作る。永続化・他セッションへの復元・入力からのデシリアライズはしない。
軽量検査から新規発行・更新しない。失効後や全体再検査の失敗後は再利用せず、
完全な検査が改めて成功した場合にだけ発行できる。

結果を所有FS・選択中のgeneration/root・lease/session・初回import transaction・
親子job ID・正確な完了参照・初回metadata/change証拠へ束縛する。filename、
size、digestまたはProject IDだけで別の入力と同一視しない。保持する管理値は
所有した不変コピーであり、GS係数やZIP全体の配列は保持しない。

既存descriptorは原本・manifest・metadataのhash、source proof、rootを持ち、
子完了記録はstart/journal/初回publicationに、親完了記録は正確な子完了記録に
対応している。現時点では新wireや永続receipt形式は不要と考えるが、実装前の
設計レビューで確認する。必要になれば別の承認対象として止める。

## 4. 通常の各操作でも維持する検査

1. 選択中generationとleaseの開始・終了監査、およびawait後の有効性確認。
2. 有限のjob/index/backlink探索と、recipe・metadata.am・親子管理記録・完了参照の
   正確な比較。対象のZIPが存在し、正しい大きさであること。
3. 現在のmetadata・journal parts・初回original changesの包含、現在のモデル／
   画像・CAS・必要な検証証拠と、新たな出力元／生成物の既存の検査。
4. 欠落・不一致を、キャッシュや受信ファイルから補完しないこと。

通常の後続編集でcurrent headsが進んでも、検証済みの初回取り込みとの関係を
毎回確認する。不一致・監査失敗・lease喪失・Project切替・終了・generation/root
変更・復元／受信／復旧の開始で一時結果を失効させ、従来の全体検査へ戻す。

## 5. PO判断が必要な挙動の違い

**取込時の私的ZIPだけが、作業中に同じサイズで変更・破損した場合、その検出は
次回の全体検査（開き直し・復旧等）まで遅れる。** GS payloadだけでなく、ZIP内の
header・manifest・CRC等の同じサイズの破損も含む。receiptの比較だけでZIPの
現在の内部内容を確認したことにはならない。

ZIPの欠落・長さの変更、管理記録・metadata・recipeの変更、journalの欠落は通常
操作でも検出する。現在のProjectのasset等に対する現行の検査もすべて維持し、
そこで見つかる不整合は即時停止する。原本そのものは保持する。
一時結果は破損ZIPを新たな入力として許可せず、次回起動・復旧で全体検査に失敗
した場合は修復必要状態で停止し、後続の編集・現在の保存データを変更しない。
キャッシュによる原本の自動修復や、後続編集を捨てる再取り込みはしない。
この破損ケースの復旧UIが対応済みとは主張せず、実装前に利用可能な復旧経路を
確認する。未接続の復旧ケースは未受入れとして残し、復旧対応済みと数えない。

現行コードでは、修復必要状態の既存Projectへ同じ環境でバックアップを復元する
入口も`ready`を要求する。検査済みバックアップを空の別環境で開く経路はあるが、
復元できるのはそのバックアップに含まれる編集までである。それより後の編集は
元の保存領域に保持されても、このケースから救出する利用者向け導線は未接続。
本案の有効化に先立って、この作業保全・復旧導線を具体化し受入れを確認する。
そこが未確定の間は検査タイミング変更を保留し、現行の検査を維持する。

現在の[01e §8](01e-desktop-large-gs-workflow.md)と
[06 §§12.1／12.6](06-project-package-wire.md)は、Session読取や親子照合時にも
正確な入力ZIPの検査を求める。本案はその検査タイミングを変更するため、
[AGENTS.md](../../AGENTS.md)の設計・保存／復旧契約変更の規則に沿った事前判断が必要。
承認前は現行の全体検査を維持する。

変更対象は、初回の完全な親子完了後に限った`Session.read`内のimportClean
`CleanInputJob.open().validateJournal()`と、`assertReviewEditSlot`／
`reviewEditStates`／子binding・completion照合に含まれる完了済み原本ZIPの
再検査である。未完了処理や新しい入力の検査まで省略する意味ではない。

## 6. 実装承認後の受入条件

- 既存の未完了親子処理・原本／管理記録／証拠の欠落・改変・中断・再試行の拒否を維持。
- 全体検査済みの同じセッションで、実編集→保存→追記→再保存が成立する。
- 管理記録、metadata、journal、現在のCASやZIPの欠落・長さ変更で即時停止し、
  補完しない。操作失敗時も作業記録を保持する。
- 同じサイズの私的ZIP破損について、通常操作時の遅延検出を明示的に検証し、
  開き直し・復旧では全体検査が拒否する。現在のProjectの破損とは混同しない。
- 別FS／root／generation／job／session、lease喪失、切替、受信・復旧時に結果を
  使い回さない。正常な後続編集の原履歴・ピン座標・添付は維持する。
- 50万点GSのコピー→実編集→保存→完全終了→再開で、各操作の時間と原本digest／
  全記録の一致を検証する。小さい入力・通常の全体検査経路も回帰確認する。
- 独立レビューと必要な最終チェックを実行する。公開・一般採用の承認にはしない。
