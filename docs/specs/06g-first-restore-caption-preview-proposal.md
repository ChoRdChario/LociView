# 06g 初回復元中の記録先行表示

Status: **PROPOSED — PO未承認・未実装**。現在の製品契約は変更しない。

## 1. 利用者が先にできること

初回バックアップ復元では、入力ファイルを検査できても、復元先の初期化が終わるまで
記録を読めない。固定バックアップの各3回比較では、変更前の記録表示の中央値は
Ki-84約59秒、50万点GS約112秒だった。通常再開の本文表示約5.4／6.3秒とは別の経路である。
測定条件・入力識別・各回の値・最終候補の結果は[todo](../../tasks/todo.md)が管理する。

提案は、**検査済みの入力ファイルのタイトル・本文を、初回復元の書込み中にも閲覧・検索できること**。
編集・保存・画像・3Dの利用開始を前倒しする案ではない。原本・画質・オフライン利用と、
書込後の全量照合・Selection・公開・中断復旧を維持する。新しい容量・速度保証は作らない。

## 2. 今回必要な判断

[06aの「Read-only text during first restoration」](06a-first-backup-open-proposal.md)は、
初期化後の検証済みProjectDisplayからの表示に限定し、未初期化archiveの候補や推測したScene/tokenを除外する。
[06e §9](06e-selected-generation-output-read-proposal.md)の通常再開通知も初回復元を対象にしない。
現Hostの順序はinitialize→projection→display callback→Selection→adoptionである。

これに「入力検査済み・復元未完了」という読み取り専用表示の根拠と所有期間を追加する判断が必要。
既存callbackの接続変更だけとは扱わない。PO承認と独立した契約・安全性レビューを経てから実装する。
通常のSessionやProjectDisplayを偽装せず、初期化完了・保存完了の検査結果へ流用しない。

## 3. 対象と境界

- 元Projectが端末にない初回バックアップ復元だけを対象とする。同じ処理の再試行も、
  再選択した原本の必要な再検査が成功してから新しい表示を作る。
- 既存Projectへの置換・マージ・返送、Native/v1/LociMyu変換、通常再開の契約は変更しない。
- 既存のファイル検査・復元Job・Session・WorkspaceFSの権限を維持する。
  UIにpackage読取、直接storage操作、編集コマンドを渡さない。
- wire形式・保存schema・永続ID・変換ID・依存・rendererを追加しない。一般公開・実機Safariの合格も含めない。

## 4. 表示用情報と寿命

内部の読み取り専用情報`FirstRestoreCaptionPreview`を、復元処理のHost境界で作る。
これは実装時の型設計の要求であり、新しい保存形式ではない。

- 入力の既存検査が要求するcontainer／manifest／全量照合と、原本metadataの構造・履歴・参照・
  予算検査をすべて通過した結果だけから作る。名称やファイルサイズによる信頼推測は行わない。
  表示を速める目的で検査を省略・遅延しない。既存の検査済み結果を使える寿命は拡張しない。
- 内容は入力のProject識別情報と原本履歴を照合する既存の事実、Project名、
  正当に解決できた起動Sceneと所属、Caption ID・タイトル・本文。
  Scene/CaptionのIDと所属は承認済みの原本解決規則を使い、新しい対応付け・推測IDを作らない。
  原本が許容する曖昧さや競合を「唯一の値」と決め付けず、利用できる解決済み値だけを表示する。
  解決できない部分は短く表示し、復元処理自体の既存の受入れ・拒否条件は変えない。
  起動Scene・lifecycle・membership・競合の解決は実装前レビューで具体化する。
  診断用`unambiguousRecords`だけをScene providerとして扱わない。先行表示中のScene切替は追加しない。
- 通常のSession tokenとは別の、復元試行だけが所有する一時的な参照を付ける。
  入力・処理・対象の一致を確認してからUIへ通知し、終了後や別処理からの通知は不採用にする。
- 同じCaptionの本文をScene数だけ複製しない。既存metadata予算内の情報を使い、
  原本ZIP、画像、モデルの新しいcopy、デコード済みcache、GPU資源をこの表示に所有させない。
  全量検査に必要な読取まで削る意味ではない。
- 成功時は生成側と以後の通知を失効させる。UIがすでに所有する文字列・IMEだけは、
  同じ所有者のguard下でhandoffまで保持できる。失敗・取消・dispose・権限喪失・入力変更では破棄する。
  表示情報や検査済み証拠を次の試行の信頼根拠としてcacheしない。
  UIの検索語・選択は内容を保証する証拠に使わない。
- 表示用抽出だけの失敗、解決できる起動Sceneの不在、通知先の例外ではpreviewを取り下げ、
  正常な復元へ新たな失敗条件を加えない。本体検査の失敗は従来どおり拒否し、隠さない。

## 5. 画面と完了への引継ぎ

既存の復元準備画面と本文readerを使い、別の管理画面や出力種別を増やさない。
表示中は「復元中」と「最初のシーンの記録を読めます。編集・保存は準備完了後に使えます。」を近くに示す。
完了表示・保存済み表示・通常の編集画面はまだ表示しない。

検索と本文選択はUI内で完結する。タイトル・本文は既存の安全なplain-text表示を使い、
画像やHTML、外部resourceの取得を開始しない。未準備の写真・3Dは利用可能と見せない。
進捗と失敗時の復旧操作を隠さず、既存Jobが許していない取消・再選択を追加しない。

通常画面への引継ぎは、既存の初期化・保存後照合・Selection・adoption完了後だけ行う。
Hostが保持する入力proof・原本履歴の識別事実と実際のreadyな復元結果が一致し、
同じ入力・Job・所有者かつProject/Scene/Captionの一致を確認できた検索・選択だけを引き継ぐ。
通常画面のactual tokenが現在の実結果に属することも確認し、一時的なpreview参照をSession tokenとして扱わない。
IME入力中は勝手に置換せず、準備完了を示して入力を終えられる表示をguard下で保ち、
終了時にactual tokenと所有者を再確認して切り替える。別入力や別Jobの選択を引き継がない。
読取中の内容を通常Sessionの確認済み結果として渡さず、通常画面は従来の実結果から作る。

失敗時はreaderを破棄し、元の失敗・原本保持・中断記録と既存の復旧導線を表示する。
プレビューが見えたことを復元の成功と扱わない。

## 6. 実装前・接続前の受入れ

実装前に既存の原本検査がこの通知に十分な結果を返せることと、その所有期間を独立レビューする。
追加の検査が必要なら実時間も測定し、重い反復検査や新しいcacheを暗黙に導入しない。
解決済みの所属を安全に得られない場合は、この範囲を勝手に広げず設計へ戻る。

- 初期化の書込みをholdし、元表・承認済み対応規則と一致するCaption/SceneをPC・touchで検索・閲覧できる。
  編集・保存・画像・3Dの利用が始まらず、成功表示にならないことを確認する。
- 入力破損、履歴・参照・CRC/SHA不一致、書込・読戻し失敗、権限喪失、Job終了・再選択、
  古い非同期結果の到着時に、既存の拒否と復旧を保ち、別データのreaderを残さない。
- preview固有の抽出・通知例外と起動Scene不在ではpreviewだけを取り下げる。
  IDだけ一致して履歴やactual tokenが異なる場合、検索・選択を引き継がない。
- IME、画面縮小、縦横変更、検索・選択の適切なhandoffと破棄、失敗の読み上げを確認する。
- 初期化後の編集→実ファイル保存→別環境復元→再編集、既存中断復旧、完全終了後offline再開を通す。
  原本・本体・画像・履歴・所属の照合は既存サービス試験と代表file flowを再利用する。
- 固定Ki-84/50万点GSの各3回で、受付、入力検査完了、本文閲覧、編集可能、3D準備を分けて測る。
  保存・再開の待ちと資源負荷を悪化させず、本文を先に読める効果を確認できた場合だけ接続する。

現行版の合格結果は本提案の検証へ読み替えない。実装後の最終diffの独立レビュー、
checkpoint・隔離・PC/touch・offlineの必要な試験を経て、todoへ正確な実行範囲を記録する。
