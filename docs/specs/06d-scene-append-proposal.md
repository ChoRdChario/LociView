# 06d — シーンZIPを既存プロジェクトに追加する案

**PROPOSED**。既存の[シーンZIP](05-project-scene-team-workflow.md#73-reviewshare)を
既存プロジェクトへ追加する製品方針は承認済み。§5の保存・復旧方式は技術案で、
旧版での端末内再開に関する判断を待つ。閲覧、単独の編集コピー、同じプロジェクトの
更新受信は、それぞれ現行契約に従う。

## 1. 取り込み時の選択

「ファイルを開く」で選んだシーンZIPは、これまでの閲覧を入口とする。既存プロジェクトに
入れる場合は「既存に追加」を選び、取り込み先とシーン名、モデル・記録・添付の範囲を
確認してから確定する。単独で作業したい場合は既存の「編集コピーを作る」を使う。

最初の対応は、元と取り込み先の物理単位が明示され、1座標単位あたりの長さが一致する
場合とする。プロファイルも同じ対応済みのものに限る。単位不明・不一致やプロファイル差が
あるときは理由を示し、単独で開ける。既存モデルとの自動位置合わせは今回の追加操作に含めない。

## 2. 追加する範囲と既存の記録

- シーンは元の名前と新しいIDで末尾に追加する。既存プロジェクト名・初期シーンと既存の
  モデル、記録、材質は保持する。追加完了後は新しいシーンを画面で開ける。
- ZIPに含まれるモデル・ピン・記録・視点・添付を一組として追加する。同名・同じ素材の
  モデルや記録も別のIDとする。検証済みで同じバイトの素材だけを保管時に共用できる。
- [ProjectFrame](01-domain-rendering.md#21-frames)の向きは共通の規則を使う。
  プロジェクト座標で持つピンと視点は取り込み先の座標系に結び付け、モデル内のピンは
  追加するモデルのローカル座標を保つ。配置、倍率、視点の数値を引き継ぐ。既存モデルとの
  位置合わせが必要な場合は、利用者が別途行う。
- 既存の[シーンから編集用データを作る変換](../../src/projectPackage/reviewSnapshot.ts)を
  対応付けの出発点とする。対応モデルのない記録、未配置のピン、確認が必要なピンの
  区別を保持する。材質の適用範囲と優先関係は保持し、共通材質の対象も新しいIDのモデルに
  限る。開始視点は追加したシーンへ引き継ぐ。
- 元のZIPに含まれる情報だけを取り込む。取り込みの名称で履歴の統合を示さない。

## 3. 確定と中断復旧の設計条件

確定まで書き込みを行わない。確定時に編集ロックを取得し、取り込み先の保存済みの版・座標系、
対象ZIP、表示した内容、追加後の容量と対応形式を再照合する。取り込み先が更新されていれば
確認へ戻る。元のZIPの照合値、取り込み先、追加用のID対応を1回の処理に固定する。
素材の検証・保存後の照合と、現在の作業を公開する境界には既存のSessionとジャーナルを
使う。中断した場合は最後に公開した内容を保持し、復旧を案内する。追加の結果は検証後に
一括で公開する。復旧には同じZIPと同じ処理の記録を使い、再試行や連打は一度の追加に束ねる。
完了後に利用者が同じZIPを選び直して追加を確定した場合は、別のシーンを作る案とする。
開始前は取消を受け付け、開始後は既存の復旧規則に従う。

保存レシート、対応プロファイル、中断時の扱いは§5の技術案に定める。

## 4. 確認項目

- PCとタッチ画面で、閲覧、追加先の確認、取消、追加を通す。
- 同名のモデルや記録があるデータで、既存データと追加データのID、位置、開始視点、
  モデル・添付のハッシュを比較する。元ZIPを単独で開いたときの見え方とも照合する。
- 未対応の単位・形式、容量超過、別タブでの編集中、書き込み開始前の取り込み先変更、
  改変ZIPを拒否し、
  元ファイルと手元の記録を保持する。
- 中断後に別のZIPを拒否し、同じZIPで復旧する。保存・再開を通し、追加シーンが
  1つだけであることを確かめる。

## 5. 技術案 — 端末内の追加を一度の変更として公開する

### 5.1 追加データの組み立て

閲覧中の検証済みReviewを使い、取り込み先を読み取り専用で開いて、対象Projectの由来、
公開版、座標系とプロファイルを取得する。`map1 → map1`、`map2 → map2` の組だけを扱う。
Reviewと対象双方の `metersPerProjectUnit` が定義され、数値が厳密に一致することを確認する。
確定時は編集ロック下で同じ公開版を確認する。変更されていれば、追加内容の確認へ戻る。

`prepareReviewEdit` で追加する記録と型別の新規IDを生成し、再試行時の対応表を固定する。
一時的なプロジェクトの識別子・タイトル・初期シーンは取り込み先に渡さない。取り込み先の
実在する有効シーンの末尾より後ろに順序キーを割り当て、プロジェクト座標のピンと保存視点
だけを取り込み先の座標系IDへ結び付ける。取り込み先にすでにあるIDとの衝突、解決できない
順序、検査・メタデータ容量の超過は、書き込み前に拒否する。追加する記録だけを取り込み先の
履歴に一つの変更として追加し、既存の編集履歴を保持する。書き出し時はこの変更を現行形式の
履歴として扱う。

### 5.2 記録と公開

`v2/packages/scene-append/<処理ID>/` に、以下を既存の書き込み・読戻し規則で保存する。

| 記録 | 内容 |
| --- | --- |
| `input.json` | 仕様識別子、処理ID、元ZIPのSHA-256と長さ、検証済みスナップショットの参照、対象Projectの由来・公開版・先端、追加シーンID、ID対応表、追加する変更の参照、素材の全一覧と確定時の新規保存分 |
| `change.amchange` | 確定した1件の変更の元バイト。再試行時にも同じバイトを使う |
| `bound.json` | `input.json` と `change.amchange` の照合完了を示す参照 |
| `abandoned.json` | ジャーナル開始前に行う取消。照合済みの処理では `bound.json` を参照する |

正式なローカルジャーナルに `appendScene` 種別を追加する。開始記録に `bound.json` の
参照を持ち、確定ダイジェストにこの参照と新規素材の完全な一覧を含める。ジャーナルの
処理IDは追加処理IDと共通にする。既存の `planReceived` で対象全体の容量と素材・プロファイルを
検証し、既存素材は照合済みのものを使う。新規素材・確認結果を保存して読み戻した後に、
既存のジャーナルとSessionで1件の変更を公開する。共有の基準版は追加しない。
照合済み素材が途中で増えても、新規保存分の記録は確定時の一覧を使う。追加に使う素材は
新規保存分と再利用分の両方を記録し、準備完了後にもその全体を検査できるようにする。
未完了の処理は、ジャーナル開始前から通常の編集・共有・受信・復元の可否に反映する。

### 5.3 復旧と旧版との互換性

- `bound.json` 前の未完了記録からは書き込みを開始できない。正常な記録が途中まである
  場合は、ジャーナルが始まっていないことを確認して取消できる。破損した記録は修復へ
  案内する。照合完了後からジャーナル開始までに別の版で対象が編集された場合は、古い
  処理を取りやめ、現在の版で追加内容を確認し直す。
- 記録の照合後からジャーナルの準備完了までは、元ZIPの選び直しを求める。元ZIPの
  SHA-256・長さと保存したID対応を再照合する。元ZIPは処理の入力として使い、端末内に
  もう一つの完全なZIPを作らない。書き込み前に元ZIP・保存した1件の変更・対応する
  追加データの一致を検証する。保存した変更を再生成せず、元の操作を展開して、追加対象
  への記録だけを書き込むことと、対象Projectの公開版を親とすることを照合する。
- ジャーナルの準備完了後は、記録済みの変更・素材・取り込み先を再照合して再開する。
  完了は同じ処理IDの公開記録と追加変更で判定する。その後に編集があっても完了済みと
  判定し、同じ処理を再適用しない。現行の復旧画面で未完了処理を案内する。
- 現行の旧版は `appendScene` の端末内記録を解釈できない。追加を行ったプロジェクトを
  **同じ端末内データから再開するには対応版が必要**になる。対象は追加用ジャーナルの開始後。
  既存のプロジェクトを対応版で開くだけではこの記録を作らない。ZIPの形式は変えず、対応版から書き出したZIPを旧版で
  開ける条件は、既存のメタデータ・素材プロファイルと必須機能の条件に従う。

従来の `localCommand` は素材の新規追加を1点または既定のメディアの組に制限する。
シーン追加では複数素材を1回で検証し、同時に公開するため、旧版互換性を判断した後に
この技術案を実装する。既存のジャーナルとZIPの検証規則は引き継ぐ。
