# 通常保存の本体検査を出力時へまとめる評価案

Status: **PROPOSED — PO未承認、未実装**（2026-11-15）。
対象は通常の「ファイルに保存」だけ。速度改善は未確認であり、数値の保証はしない。
現在の実装と検証は[todo](../../tasks/todo.md)で管理する。

## 1. 利用者の結果と判断対象

原本・画質・履歴を保持し、完成した保存ファイルの独立した全量照合と中断復旧を維持する。
書き出し前のモデル・写真などの全量読み取りを、すでに存在する生成時の全量照合へ移す。
存在・容量・保存記録の確認と、記録・共有履歴・保護対象の整合確認は開始前に残す。

同じ容量のまま壊れた素材は、出力の開始後に検出する場合がある。
その場合は一時的な出力データが残ることがある。検証済みの完了記録やダウンロードは渡さず、
元のProject・本文・原本を変更して帳尻を合わせない。既存の中止・再試行・整理で扱う。

判断対象は、この**不正な本体を検出する時点の変更**を限定評価してよいか、という一点。
承認後も、実時間の効果と安全性を確認できた場合だけ通常PC候補へ接続する。
小さな回数の削減しか得られない場合や、新しい汎用的な仕組みが必要になる場合は採用しない。

## 2. 現在の処理と根拠

`BackupSourceCapture.collect()`は、metadata・交換基準・evidenceから対象一覧を作った後、
各CAS本体を`checkedBlobStream`で全量読み取る。この読み取りはサイズ・SHA-256・
stream budgetの確認であり、モデル／画像の新しい表示情報やevidenceを生成していない。

生成側も同じ固定済み`manifest.blobs`を走査し、対応する`bodyRefs`を要求し、
期待するSHA-256と長さを照合してZIPへ書く。現在の素材だけでなく、競合中の値や
交換基準だけが保持する素材も含む。保存後は別にファイルを開き、各entryのSHA／CRCと、
Backupの保護対象・交換基準を照合している。これらは独立して残す。

計測上の`stream-close`は、素材読取・hash・ZIP生成・書込・実際のcloseを含む処理全体である。
OSのcloseだけが遅いとは判断しない。事前の本体走査を減らしても、生成側の時間や
ファイルキャッシュの条件が変わる可能性があるため、合計の実時間で評価する。

## 3. 実装する境界

- `projectPackage/backupSource.ts`へ、通常出力専用の名前付き準備入口を設ける。
  `MetadataProjectSession`の通常保存だけが使用する。汎用的な「検査済み」flag、
  任意caller向けの検査省略option、Sessionをまたぐcacheや新しいstream proofは作らない。
- 既存の`prepare()`と`restore()`は全量検査を維持する。共有作業一式・変更分・閲覧用出力、
  復元・取り込み・その他のcaptureへ変更を広げない。共用の`collect()`のloopを
  そのまま全callerから削除してはならない。
- metadata本体・交換基準・evidence・対象集合・保護対象・必要能力と、準備前後の
  source／publication／基準一致を従来どおり検査する。対象は従来の本体集合と完全一致させ、
  競合・基準専用・原本を含める。metadataから計算する件数・容量budgetも維持する。
- 通常出力の準備では、各対象の`openReadOnly`による保存記録・suspect状態・存在・
  実際のサイズを確認する。本体stream／readerを作らず、fileの観測をcaptureへ保持しない。
  明示的な解放APIがないため、native Fileの解放時点は保証しない。
  返すcaptureは従来どおり所有したmetadata／evidence bytesと値だけとし、readerを保持しない。
- 生成は固定済みの期待SHA・長さに対し、既存の全量照合とstream budgetを適用する。
  読み取れた不正bytesに合わせてmanifest・metadata・期待digestを書き換えてはならない。
- 書いたファイルの独立した全量検査、入力管理情報の読戻し、書込前後・確定・
  中断復旧の検査を維持する。完成検査前の成功表示・`artifactVerified`等の完成receipt・
  ダウンロードは禁止する。準備・開始の記録は、完成を示す記録と区別する。
- 個別の`outputReady`、source capture、writeの所有期間は現状を維持する。
  取り込み元ZIPの検査共有を複数の確認へ広げる案や、buffer／bridge変更は含めない。

公開ファイル形式・schema・変換ID・依存・容量枠・画質・画面操作は変更しない。
評価で不採用なら、追加の入口を未使用のまま積み残すことを避け、従来方式へ戻す。

## 4. 受入れ確認

- 欠損・サイズ違い・suspect本体は、出力準備の永続化より前に拒否する。
- 現在使用中、競合中、基準専用の各本体を同じサイズで改変し、生成時に拒否する。
  期待digestは変えず、完成receipt・ダウンロード・完成扱いを残さない。
- stream budget違反、途中変更、権限喪失、取消、読取／write／close失敗を既存の
  service試験で確認する。書いたファイルの改変・読戻し失敗の既存試験は変更しない。
- 途中の出力は同じ固定済み情報で再試行でき、中止操作も利用できることを確認する。
  中止は一時データを保持する。未確認の出力データは既存の別の整理操作で扱い、
  中止しただけで削除されたことにはしない。
  二重の履歴を追加せず、編集を続ける場合も、古い期待digestを新しい値へ差し替えて救済しない。
- 復元と従来のcaptureは事前の全量走査を維持し、変更が漏れていないことを確認する。
- Ki-84と50万点SH4を別々に、同じ入力・履歴・ブラウザ・画面・安定した通常負荷で
  対策前後各3回測る。Source収集、生成／書込、保存後照合、downloadへの引渡しを分ける。
  診断付き計測と通常時間を混ぜない。回数の減少だけで効果を主張しない。
- 独立した設計／最終差分レビュー、影響するPC・スマホ相当の実ファイル／再開、
  必須checkpointと隔離検査を通す。変更のない大きな往復は項目ごとに増やさない。

iPhone実機、一般公開、rendererの軽量化、全く別の保存方式は含めない。
本案の承認は、その実機・採用・公開gateの合格を意味しない。
