# HEICの権利・配布条件と、デコーダを同梱しない代替手段

調査日: 2026-10-30。**調査結果・未承認の設計候補**。法的な許諾確認、製品採用、
配布承認、実装・実機検証の完了を示さない。POは権利の再整理と、スクリーンショット等の
力技を含む代替手段の検討を依頼した。実行結果と次工程の正本は[todo](../tasks/todo.md)。

## 結論

現在の同梱デコーダの停止理由は、固定したPoCの技術的失敗ではなく、配布・権利の判断が
未完了であること。これは「HEICの扱いが一律禁止」「必ず有料」と判明したことではない。
一方、OS任せにした全Windows対応や、全HEICの向き・色・HDRまで解決済みともいえない。

最初に優先したいのは、**表示できるOS・アプリでJPEG/PNGを用意し、LociViewにはその画像を
追加する流れ**。画像の貼付けを足す候補なら、既存の保存・共有形式を変えずに操作を減らせる。
非対応端末でも原本を含め共有するには、HEIC原本と表示用画像の組を扱う新しい契約が必要になる。
現行の対応ブラウザでも、HEIC原本を保持して保存することは既にできる。

画面表示・スクリーンショットでも、表示元のどこかではデコードする。
設計上の狙いは、その処理を既存OS・アプリ・対応端末へ任せ、LociViewからHEVCデコーダを
配布する必要を減らすこと。これだけで、すべての権利確認が完了するとは説明しない。

## 権利の論点を分ける

### ソフトウェアの配布条件

評価済みのlibheif1.23.3・libde2651.1.2にはLGPLv3の条件がある。§4は、表示・ライセンス添付・
改変可能性・再リンクまたは適切な置換可能性等の条件を満たすCombined Workの配布を定める。
LGPLだから商用不可、静的Wasmだから一律不可、アプリ全体を必ずGPLにする、という整理はしない。
正確な配布物について、ソース・bridge・ビルド設定・Application側の再リンク材料・置換手順・
noticeを利用者にどう渡すかが未確定である。
[libheif固定版のCOPYING](https://raw.githubusercontent.com/strukturag/libheif/v1.23.3/COPYING)、
[libde265固定版のCOPYING](https://raw.githubusercontent.com/strukturag/libde265/v1.1.2/COPYING)。

### HEVC特許

上記のソフトウェア条件と、HEVC標準実装に関する特許の扱いは別の確認事項である。
Access Advanceの現行FAQは、無料ダウンロードのHEVCソフトも一般にはライセンスの対象となり、
例外の適用は個別ソフトについて確認するよう案内している。無料・OSS・ローカル処理という理由で
自動的に不要とは結論しない。同時に、LociViewに料金や契約が必須と確定したとも扱わない。
[現行の公式FAQ](https://accessadvance.com/faq/)。

2016年の発行元発表には、端末購入後に取得する汎用CPU上のアプリ等について、
ライセンス・ロイヤルティを求めない方針がある。ただし、現行FAQと製品の具体条件を確認するための
歴史的材料であり、現在のLociViewを無条件に免除する根拠にはしない。
[2016年の発表](https://www.prnewswire.co.uk/news-releases/hevc-advance-announces-royalty-free-hevc-software-602452325.html)。

旧Via-LAのHEVC/VVC事業は、公式ページでは2025年12月にAccess Advance側へ移管されている。
ライセンシー一覧の会社名だけで、その会社の特定製品や今回の利用まで許諾済みとは判断できない。
一つのプールの条件・免除を、全権利者についての確認済み扱いにもしない。
[現行HEVC/VVCプログラム](https://www.via-la.com/licensing-programs/hevc-vvc/)。

HEIFコンテナと、その中のHEVC画像も区別する。Nokiaの現在のHEIF参照実装は、
評価・テスト・研究向けの独自ライセンスであり、製品利用には別途問い合わせる案内がある。
これはその参照コードの条件であって、すべてのHEIFパーサに同じコードライセンスが適用される
という意味ではない。コンテナだけを扱えば、あらゆる特許確認が不要とも決めない。
[Nokia公式README](https://github.com/nokiatech/heif/blob/master/README.md)、
[同LICENSE](https://github.com/nokiatech/heif/blob/master/LICENSE.TXT)。

## 代替手段の比較

以下の実用性・優先度は、公式資料と現行コードからの設計上の評価。今回の実機実行結果ではない。

| 手段 | 利用者の流れ | 画質・手間と限界 | 現在のLociViewとの関係 |
|---|---|---|---|
| OS・対応端末でJPEG/PNGを書出し | Mac等でHEICを開く→別形式で保存→メディアを追加 | 元画像の画素寸法を使いやすく、画面撮影より優先。向き・色・メタデータは出力条件による | 生成済みのJPEG/PNGファイルは既存経路で追加可能。HEICはProject外に別保管 |
| 画像をコピーして貼付け | ビューアの「画像をコピー」→LociViewで貼付け→画像確認 | ピクセルが渡る場合は画面の解像度に縛られにくい。ファイルやパスだけをコピーするアプリもある | 貼付け入口は未実装。PNG/JPEGの実データを既存の検査・追加サービスへ渡す候補 |
| 範囲スクリーンショット | HEICを表示→画像部分を撮影→PNG/JPEG保存、または貼付け | 現実的な救済。表示倍率・画面解像度・余白に左右され、原本のHDR・撮影情報等を再現する手段にはしない | 保存したPNG/JPEGは追加可能。貼付けは上記の新規入口が必要 |
| 対応ブラウザで一度だけ表示用画像を生成 | HEICを選ぶ→標準デコード→canvasからPNG/JPEGを生成 | 画面撮影より元画素を使いやすく、自動化の本命候補。向き・色・HDR・資源上限は別途検証 | 原本と一緒に共有しWindowsで使うには新契約。現在は未実装 |
| アプリから画面を取得 | 利用者が外部ビューアを選ぶ→1画面を取得→切抜き・確認→PNG化 | ファイル保存を省けるが、毎回の画面選択と許可、取消・取得停止が必要。周囲の情報も取り込み得る | `getDisplayMedia`の入口は未実装。貼付けより後の候補 |
| 内包済みJPEGプレビューの抽出 | HEIC内の項目を検査し、既存JPEGが実在する場合だけ取り出す | HEVC本体をデコードせず済む可能性。JPEGがない、低解像度、サムネイルもHEVCの場合は使えない | 現在のパーサには未実装。限定的な低解像度救済としてのみ検討 |
| OS画像機能を使う小さな補助ツール | 導入済みOSコーデックでJPEG/PNGを作り、通常ファイルとして追加 | 複数枚を省力化できる候補。環境依存と導入・保守の手間が増える | WebからWin32 WICを直接呼ぶ経路はない。別ツール等の設計・検証が必要 |

MacのPhotos／Previewで別形式を書き出す手順と、転送時に互換形式になる場合があることは
Appleが案内している。自動変換は常に保証されるものとせず、得られたファイルを検査する。
撮影設定を互換性優先へ変える方法は今後の撮影に有効だが、既存HEICの救済とは分ける。
[AppleのHEIF変換・転送案内](https://support.apple.com/en-ca/116944)。

繰り返す場合は、ショートカットの画像形式変換・保存をまとめる方法も候補になる。
具体的なHEICの連携は今回未検証。
[Appleの変換アクション](https://support.apple.com/en-ae/guide/shortcuts/apd1d9413cfb/10.0/ios/27)。

Windowsの範囲撮影・コピー／保存はMicrosoftの案内に沿う。貼付けには実画像のデータが必要で、
HEICファイルをコピーしただけでPNG化されるとはしない。W3CのClipboard文書には画像データと
paste経路が規定されているが、利用するOS／ブラウザでの実データは検証が必要。
[Microsoftの画面コピー](https://support.microsoft.com/en-us/office/copy-the-window-or-screen-contents)、
[W3C Clipboard API and events](https://www.w3.org/TR/clipboard-apis/)。

Safari17のHEIC対応と、canvasの画像出力APIは、上記の自動生成案の技術的な根拠である。
画素寸法が同じでも、色域・HDR・精細さ・メタデータまで原本と同一になるとは約束しない。
[WebKit Safari17](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/)、
[HTML canvas画像出力](https://html.spec.whatwg.org/multipage/canvas.html#dom-canvas-toblob-dev)。

画面取得では利用者の操作・対象選択・明示許可が必要で、許可の永続化や対象の強制指定を前提にしない。
選択した範囲を確認してから保存し、取得後・取消時には即時停止する設計が必要になる。
[W3C Screen Capture](https://www.w3.org/TR/screen-capture/)。

HEIFはJPEGも格納できるコンテナであるため、内包済みJPEGの抽出は限定候補になる。
「全HEICにJPEGプレビューがある」という根拠や実ファイルの検証結果は今回得ていない。
OSのWIC経路も、コーデックが存在し実際にデコードできることを別途確認する。
[HEIF参照実装の形式説明](https://github.com/nokiatech/heif)、
[Microsoft WIC HEIF codec](https://learn.microsoft.com/en-us/windows/win32/wic/heif-codec)。

### 力技で気を付ける点

- スクリーンショットが必ずPNGとは限らない。Appleの現行案内では、対応iPhoneはSDRがPNG・
  HDRがHEIF、対応MacもHDR撮影はHEIFになる。救済画像の実形式を確かめ、必要ならSDR／PNG・
  JPEGを選ぶ。上記AppleのHEIF案内と[iPhoneの取込設定](https://support.apple.com/ja-jp/guide/iphone/iph2d2500abc/27/ios/27)参照。
- どの端末・アプリでもHEICを表示できない場合、画面撮影だけでは解決しない。
- 拡大して分割撮影・結合、印刷して再撮影、別端末で画面を撮影する案も考えられるが、
  位置ずれ・モアレ・色・精細さ・操作量の不利が大きい。通常の書出しや貼付けを優先する。
- 外部クラウド変換は、写真の外部送信・保存先・サービス条件の判断が増える。
  サーバー側へ移してもHEVC処理の権利確認は残る。現在の標準導線には推奨しない。
  [Access Advanceのクラウド処理の説明](https://accessadvance.com/topic-what-do-we-license/)。
- 利用者に別デコーダを持参させる案も、権利の自動解決にはならず、設定・安全性・保守を複雑にする。
  OSの既存機能を使う案と、未確認の第三者デコーダを読み込む案は区別する。

## 現在できることと、新しい契約が必要なこと

現在の[仕様08](specs/08-daily-authoring-workflow.md)は、HEICをブラウザ標準で実際に
デコードできる環境だけに限定している。[media.ts](../src/projectFiles/media.ts)の検査は追加時だけでなく、
[content.ts](../src/projectFiles/content.ts)を介する受信・復元でも必要である。

そのため、**HEICとJPEGを現在のProjectに別々に登録するだけでは、Windows対応にならない**。
JPEGがあっても、読めないHEICの検査で受信・復元全体が拒否され得る。
[MediaResource](../src/domain/projectRecords.ts)も、原本と派生画像の関係を持たない。
HEICを別の種類として偽装してこの検査を避ける案にはしない。

契約を変えずに使えるのは、JPEG/PNGだけをProjectへ追加し、HEIC原本を別に保管する方法。
**この方法では、LociViewのバックアップに、その別保管のHEICは入らない。**
画面撮影で用意した画像は原本の完全再現ではなく、利用者が選んだ別の画像として扱う。

原本をProject内で保持する将来案は、以下を決めてから実装する。

1. 原本と表示用画像を明確に識別し、原本を黙って置換しない。
2. 対応端末での自動生成と、手動の画像コピー・画面撮影を区別し、実際の寸法・形式を表示する。
3. 非対応端末が原本をデコードせず受信できる条件と、表示用画像を失った場合の復旧を定める。
4. digest・関連付けの検査と、画面内容が原本と同じかの検証を区別する。
   デコード不能な端末は、ハッシュの一致だけで両画像の視覚的同一性を証明できない。
5. 保存・各共有目的・復元・旧版読込・容量・取消を一つの流れとして定める。
   原本に残る撮影情報等も共有範囲へ含めて説明する。

## 次工程の推奨

まず「読めない画像をJPEG/PNGで用意して追加する」救済を、既存の入口と具体的な案内で使える形にする。
新規実装の候補は、既存の`Host.addMediaFile`→検査→Sessionへ接続する**画像の貼付け**。
HEIC専用の設定を増やさず、他の画像にも使える入口を優先する。これは実装提案であり、今回の実装ではない。

原本を含むProjectの受渡しまで完成させる本命候補は、**対応端末で一度だけ表示用JPEG/PNGを作り、
HEIC原本と組にする**方式。デコーダ同梱を唯一の選択肢にせず、上記の保存・検証契約を具体化する。
画面取得APIや内包JPEG抽出は、先の簡単な方法では足りない場合の補助候補に置く。

権利について外部へ確認する場合の質問材料は、配布主体・対象国・無料公開／商用利用・静止画のみか、
Wasm同梱かOS任せか、既存無料ソフト方針の適用、プール外の権利、再リンク／置換材料の範囲。
今回、問い合わせ・ライセンス契約・支払は一切行っていない。
