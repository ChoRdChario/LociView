# 00. 設計思想 — LociViewという木の形

本資料は、個別仕様（docs/01〜07）の背後にある考え方を説明する。新しい機能を追加するとき・迷ったときに立ち返る場所。

## 1. アプリは4+1の層でできている

機能面の分解は「①セーブデータの扱い ②キャプションと座標データ ③3D描画 ④UI」の4つで正しい。ただしこの4つは**並列の枝ではなく、内側から外側への同心円（層）**であり、さらに最下層に⑤プラットフォーム層がある。

```
┌─────────────────────────────────────┐
│ ④ UI（画面・タップ・パネル）              │  ← 一番外側・一番よく変わる
│   ┌─────────────────────────────┐   │
│   │ ③ 3D描画（three.js・ローダ）     │   │
│   │   ┌─────────────────────┐   │   │
│   │   │ ② キャプション・座標      │   │   │  ← ①と③④をつなぐ「共通語」
│   │   │   ┌─────────────┐   │   │   │
│   │   │   │ ① セーブデータ  │   │   │   │  ← 中心・一番変わらない
│   │   │   │  (op-log)    │   │   │   │
│   │   │   └─────────────┘   │   │   │
│   │   └─────────────────────┘   │   │
│   └─────────────────────────────┘   │
└─────────────────────────────────────┘
  ⑤ プラットフォーム層（OPFS・共有シート・ファイル選択 = ブラウザの方言を隔離）
```

### 依存は内向きの一方通行

**外側は内側を知っているが、内側は外側を知らない。**

- UI（④）は「キャプションとは何か」（②）を知っている。しかしop-log（①）は「ボトムシートUI」の存在を一切知らない
- だからUIを全部作り替えても（デスクトップ⇔スマホで実際にそうする）、セーブデータには1バイトも影響しない
- 逆に①を後から変えると全部が揺れる。**変わりにくいものほど内側に置き、内側ほど先に・慎重に設計する**。docs/02（データフォーマット）が「★核心」なのはこのため

### LociMyuの反省がこの形を要請した

LociMyu αが49個のパッチファイルの集積になった構造的原因は、この「向き」が無かったことにある。全モジュールが `window` グローバルとカスタムイベントで互いに触り合っていたため、どこを直しても全体が揺れ、「上から貼るパッチ」でしか変更できなくなった。層と一方通行は、その再発防止装置である（docs/03 §1）。

## 2. 幹は①データ。アプリは幹に生えた葉

> **アプリは寿命が短く、記録は寿命が長い。だからアプリではなくデータを幹にする。**

- ①のop-log（JSONL）は人間可読で、10年後にLociViewが消滅してもテキストとして読める（NFR-03）
- three.js（③）が時代遅れになっても、UI（④）を何度作り直しても、幹は残る
- 「マージできる」という最重要要件は、④や③の機能ではなく**①の性質**として実現している。UIに「マージ機能」があるのではなく、データが生まれつきマージ可能な形（1編集者1ファイル追記専用）をしている。だからZIP受け渡しでもスプレッドシート往復でも、どの経路から来ても統合は壊れない

判断基準として使う: 新機能の要求が来たとき、「これはどの層の性質として実現すべきか」を最初に問う。UIの機能に見えるものの多くは、実はデータの性質である。

## 3. ②は枝ではなく「共通語（契約）」

キャプション・座標・表示セットのスキーマ（②）は、①が保存し、③が描画し、④が編集する**共有の語彙**。枝というより、枝同士が会話するための辞書に近い。

- ②の中で唯一③と深く絡むのがピンの**アンカー**（どの面のどこに刺さっているか）。ここは「データの世界」と「3Dの世界」の翻訳点として意識的に設計する（docs/04 §5）。モデル差し替え時にピンが迷子になるかどうかは、この翻訳点の品質で決まる

## 4. ⑤プラットフォーム層 — 「HTMLだから横展開できる」のではない

OPFS保存・共有シート・ファイル選択・PWAといった「ブラウザごとの方言」は⑤に閉じ込め、①〜④はデバイス差を一切知らない（docs/03 §4、docs/06）。

デバイス横展開の容易さは、HTMLを選んだ瞬間に自動で手に入るものではなく、**この隔離をサボらないことで達成される**。⑤の外にブラウザ判定の `if` を書き始めたら設計が腐り始めた兆候である。

## 5. すべての操作は同じ輪を回る

```
入力(④) → 「操作」を発行 → ①が自分のログに1行追記 → 状態を再計算 → ③④が描き直す
```

単方向のこの輪（docs/03 ProjectStore）以外の近道を作らない。UIから直接シーンを書き換えない。描画側から直接データを書かない。

**輪が1本であることの実利（例）**: 将来「2点間を測るメジャー機能」を足す場合、②に `measure` エンティティを定義し、④に測定モードボタン、③に線の描画を足すだけでよい。①のマージ機構には一切触れないのに、測定結果は自動的にマージ可能・履歴付き・スプレッドシート出力可能になる。**新機能は保存・統合・履歴をタダで相続する** — この木の形にした最大の見返り。

## 6. 機能追加時のチェックリスト

1. どの層に属するか。複数層にまたがるなら、層ごとに何を足すか分解したか
2. 新しいエンティティ種別が必要か。必要なら②に定義し、opの `e` に追加したか（未知種別は素通しされるので旧バージョンと共存できる）
3. 内向きの依存だけで書けているか。外側の事情（UI都合・ブラウザ都合）が①②に漏れていないか
4. その機能はマージされたときどう振る舞うか（op-logに乗っていれば原則自動で正しく振る舞う。乗らないローカル状態にしたなら、それは本当に共有不要か）
5. オフラインで動くか（ネットワークを前提にした瞬間、このアプリの存在理由に反する）
